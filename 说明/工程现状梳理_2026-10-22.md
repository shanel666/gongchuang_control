# 四麦轮小车工程现状梳理

> 梳理日期：2026-10-22
> 范围：当前工作区中的 Keil 工程、固件源码、现有说明和构建产物。
> 用途：作为后续按比赛流程补功能、改架构和做测试的基线。本文记录“代码中有什么、当前实际会执行什么、哪些结论尚未验证”，不把注释或旧 README 自动视为实机事实。

## 1. 工程概况

这是一个面向 STM32F103C8T6 的四麦克纳姆轮小车固件。软件已有基础外设驱动、四路闭环步进电机串口控制、JY901 兼容角度帧解析、OLED 显示和一个 5×5 静态网格 Dijkstra 寻路器。`main.c` 里还保留了指定坐标巡回路线和多段陀螺仪转向测试代码。

当前工程的功能重心仍是“按预设坐标移动和调试转向”。从本次检查到的源码看，还没有机器人端的二维码读取、物料颜色识别、机械手/夹爪控制、比赛任务状态机或成绩统计模块。物理设备是否已经装有这些部件，单靠当前代码目录无法判断。

最重要的运行事实是：当前 `main()` 在初始化串口等外设后就进入一个检查 PA8 的无限循环；PA8 的 GPIO 初始化、电机使能、路径初始化和后续路线代码都位于该循环之后，实际不可达。因此 README 中“上电自动跑路线”的描述不符合当前源码控制流。

## 3. Keil 工程配置

工程芯片设为 STM32F103C8，链接内存配置为 64 KB Flash、20 KB SRAM，工具链记录为 ARMCC 5.06 update 7。`Start/system_stm32f10x.c` 配置 72 MHz 系统时钟，`Delay_us()` 也按 72 MHz 计算。

工程有两个 Target：

| Target | 输出 | include 路径差异 | 当前判断 |
|---|---|---|---|
| `Target 1` | `Objects/Project.axf`、`Objects/Project.hex` | 包含 `app` 和 `mingling` | 现有构建日志对应这个 Target。 |
| `mingling` | 同样输出到 `Objects/Project` | include 路径没有 `app`、`mingling` | 源文件列表仍包含 36 个 C 文件；`main.c` 引用 `motor.h`、`path_planner.h`，因此这个 Target 存在头文件搜索路径风险。没有找到它的近期构建记录。 |

两个 Target 还共用输出目录和输出名，切换构建目标会覆盖同名产物。后续应明确哪个 Target 是主固件，或给不同 Target 配独立输出目录。

## 5. 主要模块和数据流

### 5.1 电机控制

`app/motor.c` 通过 USART1 发送步进驱动器协议帧：

- 位置运动命令为 13 字节，命令字节 `0xFD`；直行/后退四个电机分别设置方向，再发送同步释放帧 `00 FF 66 6B`。
- `qianjin_()`、`houtui_()`、`zuo_()`、`you_()` 参数在实现中按毫米换算脉冲；但 `motor.h` 的参数注释写成厘米。
- 平移参数为 `PULSE_PER_100CM=13008`；代码注释另写 12658，头文件也写 12658，值需要以实测和统一文档为准。
- 旋转参数为 `PULSE_PER_360DEG=17208`，源码明确标为待标定占位值。
- `shun_yaw_()`/`ni_yaw_()` 的位置模式会向地址 1–4 四个驱动器都发命令；另一个 F6 速度模式 API 只给地址 1、2 发命令。两种旋转路径不能混为一谈。
- `motor_read_pos()` 期待 8 字节位置应答并读取索引 2–7；但 USART1 中断解析器固定在收到 4 字节后置位接收标志。按当前代码，读位置接口与底层收帧长度不匹配。

### 5.2 电机应答和等待

`USART1_IRQHandler()` 以地址 `0x01`–`0x04` 作为帧头，随后固定收 3 字节，到第 4 字节为 `0x6B` 时置 `Serial_RxFlag`。`main.c` 的 `judge()` 逐个查询四个地址的运动状态，期待 `[地址][0x3A][0x03][0x6B]`，状态字节为 `0x03` 时记为到位。查询会阻塞等待，超时保护是循环计数，不是以清晰的毫秒参数表达。

历史调试记录曾报告电机 2、3、4 收不到符合预期的应答；协议字段偏移和旧版解析逻辑有差异，尚无当前原始回包证据证明这条判断已在实机闭环验证。调试时应先记录每个地址收到的原始字节，再确认统一帧格式。

### 5.3 陀螺仪

USART2 中断把收到的每个字节交给 `Gyro_ProcessByte()`。解析器等待 `55 53`，收满 11 字节后校验前 10 字节求和；通过后从字节 6、7 解码有符号 Yaw，并换算为百分之一度。`Gyro_FrameCount` 用来识别新有效帧。

`main.c` 含有一个有界的 `gyro_turn_pos_test()`：初始位置命令后按误差比例修正，最多 5 次、单次不超过 30°，使用连续 3 帧和 ±0.1° 判断成功。但它位于前面的无限循环之后，当前启动流程到不了它。另有一段较早的 PA8 转向测试逻辑，与这个函数重复，且阈值/实现不同。

### 5.4 路径规划和路线

路径图是 5×5、共 25 个节点。x 坐标为 `150, 675, 1200, 1725, 2250`；y 坐标为 `2250, 1725, 1200, 625, 150`。规划器使用四邻接 Dijkstra，所有边权均为 1，之后将结果压缩为起点、转弯点和终点。障碍配置只将网格节点设为禁行，不支持障碍区域、禁行边或运行时感知到的随机障碍。

路线执行由 `go_to()` 调用 `path_plan()`，再通过 `translation()` 将水平/垂直路段变为转向、前进或后退命令。车辆位置由程序变量记录；源码中没有把电机位置读数或环境定位传感器融合为场地坐标的逻辑，因此当前位置主要是“按命令推算”。

当前 `step` 目标与 README 所列巡回路线也不一致：README 声称中途经过 `(2250,1200)` 等一组检查点；源码 `case 4` 直接去 `(1200,2250)`，`case 7` 到配置终点后直接进入完成状态，`case 8/9` 正常状态流不会到达。

## 6. 当前 `main()` 实际执行顺序

1. 初始化 LED、OLED、按键、USART1、陀螺仪解析器、USART3 和 USART2。
2. 进入第一段 PA8 检测 `while(1)`。PA8 的 GPIO 配置写在这段循环之后，因此目前使用的是未配置的 PA8 输入；该循环没有退出条件。
3. 以下代码因此不可达：旧版 90°转动测试、PA8 输入配置、电机使能、路径障碍初始化、第二个有界陀螺仪测试循环，以及最后的自动路线 `switch(step)`。
4. 即使把前面的循环移开，当前路线 `case 7` 会设置 `step=100` 结束；`case 8` 和 `case 9` 不会被正常顺序执行。

因此当前最可靠的描述不是“上电自动运行路线”，而是“源码包含路线实现，但实际主流程仍停留在调试循环”。现有构建日志也记录了不可达语句/循环警告。
